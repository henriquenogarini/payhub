# 0.2 — Configuração

**Branch:** `feat/0.2-config`

## O que foi feito e por quê

| Arquivo | O que é |
|---|---|
| `internal/config/config.go` | Structs `Config`, função `Load()` e método `Validate()` |
| `internal/config/config_test.go` | Testes table-driven (96% de cobertura) |
| `cmd/api/main.go` | `run()` carrega a config e falha se ela for inválida |
| `Taskfile.yml` | `dotenv: [".env"]` + variável `RACE` na task `test` |
| `go.mod` / `go.sum` | Dependências `caarlos0/env/v11` e `stretchr/testify` |

A API lê **todas** as variáveis de ambiente uma única vez, ao subir, e as converte para
tipos de verdade (`int`, `time.Duration`). Se algo estiver faltando ou inválido, ela
**se recusa a subir** e lista todos os problemas de uma vez. Isso é o *fail fast*: é
melhor quebrar no deploy do que no meio de um pagamento.

O `.env` é lido pelo **Task**, não pelo código Go. Para o programa, só existem variáveis
de ambiente, que é como ele vai rodar em produção (Docker, Kubernetes, CI).

## Como testar

```powershell
task test RACE=false     # testes sem race detector (ver "gcc" abaixo)
go test -v ./internal/config/   # ver cada subteste pelo nome

task run                 # com .env:  "payhub api: starting (env=dev, port=8080)"
go run ./cmd/api         # sem .env:  erro listando DATABASE_URL, REDIS_ADDR, JWT_SECRET
```

Experimente: no `.env`, troque `HTTP_PORT=8080` por `HTTP_PORT=0` e rode `task run`.

## Conceitos de Go

### 1. Struct tags

> Em Java seria `@Value("${HTTP_PORT:8080}")` ou `@ConfigurationProperties`, e o Spring injetaria o valor.
> Em Go são **tags**: strings de metadado depois do tipo do campo, que a biblioteca lê por reflection.
> Porque Go não tem anotações nem container: nada acontece "por mágica", você chama `Load()` no `main`.

```go
type HTTPConfig struct {
	Port int `env:"HTTP_PORT" envDefault:"8080"`
}

type DatabaseConfig struct {
	URL string `env:"DATABASE_URL,required,notEmpty"`
}
```

- O compilador **não valida** tags. Um erro de digitação (`evn:"..."`) simplesmente não funciona.
  É por isso que os testes checam todos os campos.
- A mesma ideia aparece depois no Gin (`json:"name" binding:"required"`) e no Swagger.

### 2. Composição em vez de herança

> Em Java você teria classes de config aninhadas, ou uma classe base com campos comuns.
> Em Go a struct **contém** outras structs, e não existe `extends`.
> Porque Go escolheu composição como única forma de reaproveitar estrutura.

```go
type Config struct {
	AppEnv Env `env:"APP_ENV" envDefault:"dev"`
	HTTP   HTTPConfig
	JWT    JWTConfig
	// ...
}
// uso: cfg.HTTP.Port, cfg.JWT.TTL
```

### 3. "Enum" com tipo nomeado + constantes

> Em Java seria `enum AppEnv { DEV, PROD }`.
> Em Go cria-se um tipo baseado em `string` e constantes desse tipo.
> Porque Go não tem enum. O tipo nomeado já dá segurança suficiente na maioria dos casos.

```go
type Env string

const (
	EnvDev  Env = "dev"
	EnvProd Env = "prod"
)
```

Uma `string` em variável não entra onde se espera `Env` sem um cast (`Env(s)`), mas
**nada impede `Env("staging")`**. Por isso o `Validate()` confere o valor.

### 4. Retorno múltiplo e erros encadeados

> Em Java, `load()` lançaria `IllegalStateException` com um `cause`.
> Em Go a função devolve `(Config, error)`, e o erro é embrulhado com `%w`.
> Porque erro é um valor comum: aparece na assinatura e quem chama tem que lidar com ele.

```go
cfg, err := env.ParseAsWithOptions[Config](env.Options{Environment: environ})
if err != nil {
	return Config{}, fmt.Errorf("parse environment: %w", err)
}
```

Cada camada acrescenta contexto, e a mensagem final conta o caminho inteiro:

```
payhub api: load config: validate config: HTTP_PORT must be between 1 and 65535, got 0
```

- `%w` preserva o erro original, que pode ser inspecionado com `errors.Is` / `errors.As` (como `getCause()`).
- Em caso de erro devolvemos `Config{}` (o *zero value*), para ninguém usar uma config pela metade.

### 5. `errors.Join`: todos os erros de uma vez

> Em Java seria o `Set<ConstraintViolation>` do Bean Validation.
> Em Go acumulamos num slice `[]error` e juntamos com `errors.Join`.
> Porque é melhor o operador corrigir todas as variáveis de uma vez do que uma por deploy.

```go
var errs []error
if c.HTTP.Port < 1 || c.HTTP.Port > 65535 {
	errs = append(errs, fmt.Errorf("HTTP_PORT must be between 1 and 65535, got %d", c.HTTP.Port))
}
// ...
return errors.Join(errs...) // nil se a lista estiver vazia
```

`errs...` "espalha" o slice como argumentos variádicos (igual ao `String...` do Java).

### 6. Métodos e receiver de valor

> Em Java seria um método de instância, com `this` implícito.
> Em Go o método é declarado **fora** da struct, com um receiver de nome explícito.
> Porque Go separa dados (struct) de comportamento (métodos), e você escolhe valor ou ponteiro.

```go
func (c Config) Validate() error { ... }
```

| Receiver | Quando usar |
|---|---|
| `(c Config)` (valor) | O método **só lê**; a struct é pequena ou média. É o caso aqui. |
| `(c *Config)` (ponteiro) | O método **altera** a struct, ou ela é grande demais para copiar. |

### 7. Retornar valor (`Config`) e não ponteiro (`*Config`)

> Em Java todo objeto é uma referência, e passar um objeto é compartilhar o mesmo objeto.
> Em Go uma struct é um **valor**: atribuir ou passar como argumento **copia** tudo.
> Porque Go deixa explícito no tipo o que é cópia e o que é compartilhado (`*T`).

A config é lida uma vez e nunca muda. Devolver o valor é seguro, a cópia é barata e
**não existe `nil`** para checar.

### 8. Testes table-driven

> Em Java seria JUnit 5 com `@ParameterizedTest` + `@MethodSource`, e AssertJ.
> Em Go é um slice de structs anônimas + `t.Run`, e o testify faz o papel do AssertJ.
> Porque o `go test` já vem embutido: sem framework, sem anotação, só funções `TestXxx(t *testing.T)`.

```go
tests := []struct {
	name    string
	environ map[string]string
	wantErr []string
}{
	{name: "missing DATABASE_URL", environ: without("DATABASE_URL"), wantErr: []string{"DATABASE_URL"}},
	{name: "HTTP_PORT out of range", environ: withEnv(map[string]string{"HTTP_PORT": "70000"}), wantErr: []string{"HTTP_PORT must be between"}},
}

for _, tt := range tests {
	t.Run(tt.name, func(t *testing.T) {
		t.Parallel()
		cfg, err := load(tt.environ)
		require.Error(t, err)
		// ...
	})
}
```

- **`require` × `assert`:** `require` para o teste na hora; `assert` registra e continua.
- **`t.Parallel()`:** os testes rodam em paralelo. Isso é seguro porque `load()` recebe o ambiente
  como um `map` e **não mexe nas variáveis reais do processo**. Se usássemos `os.Setenv`,
  um teste interferiria no outro.
- **Testando função privada:** `config_test.go` declara `package config` (o mesmo pacote),
  então enxerga `load()`. É o equivalente a um teste no mesmo pacote Java com método package-private.
- **Struct inteira com `assert.Equal`:** igualdade campo a campo, sem precisar de `equals()`.

### 9. Os testes revelaram um comportamento real

Para `HTTP_PORT=abc`, a biblioteca reporta o **nome do campo Go**, não o da variável:

```
env: parse error on field "Port" of type "int": strconv.ParseInt: parsing "abc": invalid syntax
```

O teste foi ajustado para documentar isso (`field "Port"`, `"abc"`). É uma limitação aceitável:
o valor errado aparece na mensagem. Já os erros de **validação** (`Validate`) citam o nome da variável.

## Ferramentas: gcc e `-race` nesta máquina

O `go test -race` precisa de cgo (gcc). O gcc do WinLibs está instalado num caminho **com espaço**
(`C:\Users\Henrique Nogarini\...`), e o linker quebra o caminho no espaço. Atalho curto (8.3)
e junction não resolvem, porque o gcc converte o caminho de volta para a forma longa.

- Por enquanto: `task test RACE=false` localmente. O CI (Linux, a partir da 0.7) roda **sempre** com `-race`.
- Correção definitiva: reinstalar o gcc num caminho sem espaço (ex.: `C:\mingw64`).

## Armadilhas comuns

- **Tag com erro de digitação** (`evn:` ou `envDefalt:`): o compilador não reclama, o campo fica com o zero value.
- **Campo minúsculo não é preenchido:** a reflection só enxerga campos exportados (`Port`, não `port`).
- **`time.Duration` não é "minutos":** `JWT_TTL=15` vira 15 *nanossegundos*. Use sempre a unidade (`15m`).
- **Logar a config inteira:** ela tem segredos. Na 0.3 o logger vai mostrar só campos seguros.
- **`os.Setenv` em teste paralelo:** é estado global do processo, e um teste contamina o outro.
  Se precisar de variáveis reais, use `t.Setenv` (que proíbe `t.Parallel()` justamente por isso).

## Perguntas de revisão

1. O que é uma struct tag e quem lê ela: o compilador ou a biblioteca?
2. Por que `Validate()` usa receiver de valor e não de ponteiro?
3. Qual a diferença entre `%v` e `%w` em `fmt.Errorf`?
4. O que `errors.Join` devolve quando a lista de erros está vazia?
5. Por que `load()` recebe um `map[string]string` em vez de ler `os.Getenv` direto?
6. Como Go representa algo parecido com um `enum`, e qual a limitação dessa abordagem?
