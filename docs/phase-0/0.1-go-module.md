# 0.1 — Módulo Go e primeiro executável

**Branch:** `chore/0.1-go-module`

## O que foi feito e por quê

| Arquivo | O que é |
|---|---|
| `go.mod` | Declara o módulo `github.com/henriquenogarini/payhub` e a versão do Go. |
| `cmd/api/main.go` | Primeiro executável: `main()` chama `run()` e trata o erro. |
| `Taskfile.yml` | Atalhos `task build`, `task run` e `task test`. |

O objetivo é ter o menor projeto Go possível que compila, roda e passa nos testes.
As próximas subpartes vão preenchendo o `run()` (config, logger, servidor HTTP...).

## Como testar

```powershell
task build          # gera bin/api.exe
./bin/api.exe       # imprime "payhub api: starting" e sai com código 0
task test           # go test -race -cover ./... (ainda sem testes)
go run ./cmd/api    # compila e roda sem gerar binário em bin/
```

## Conceitos de Go

### 1. Módulo (`go.mod`)

> Em Java seria o `pom.xml` com `groupId:artifactId:version`.
> Em Go é o `go.mod`, e o **nome do módulo é a URL do repositório**.
> Porque Go não tem repositório central como o Maven Central: o caminho de import
> já diz de onde baixar o código (`go get github.com/gin-gonic/gin`).

```
module github.com/henriquenogarini/payhub

go 1.27.2
```

- A linha `go 1.27.2` é a versão mínima da linguagem que o módulo exige.
- Quando adicionarmos dependências, aparecem blocos `require` e o arquivo `go.sum`
  (hashes de verificação, parecido com um lockfile). **Os dois são versionados.**
- `go mod tidy` adiciona o que falta e remove o que não é usado. Rode sempre que mexer em imports.

### 2. Pacote = diretório

> Em Java cada arquivo declara `package com.x.y;` e a visibilidade vem de `public`/`private`.
> Em Go **todos os arquivos de uma pasta formam um único pacote**, e a visibilidade vem
> da **primeira letra** do nome: `Maiúscula` = exportado, `minúscula` = privado ao pacote.
> Porque Go prefere poucas palavras-chave e regras que dá para ver só de olhar o nome.

```go
func run() error { ... }   // minúscula: só o pacote main enxerga
```

O caminho de import de um pacote é `<módulo>/<pasta>`. Por exemplo, o futuro pacote
de config será importado como `github.com/henriquenogarini/payhub/internal/config`.

### 3. A pasta `internal/`

> Em Java seria o JPMS (`module-info.java` com `exports`), que quase ninguém usa.
> Em Go, **o compilador proíbe** que outro módulo importe qualquer coisa dentro de `internal/`.
> Porque assim o encapsulamento entre módulos vem só da estrutura de pastas, sem configuração extra.

Ela será criada na 0.2, junto com o primeiro pacote que a usa (o git não versiona pastas vazias).

### 4. `package main` e `func main()`

> Em Java seria `public static void main(String[] args)` dentro de uma classe.
> Em Go é `func main()` dentro do `package main`, sem argumentos e sem retorno.
> Porque Go não tem classes, só funções, structs e métodos.

- Um pacote `main` gera um **executável**. Qualquer outro nome gera uma **biblioteca**.
- Por convenção, cada executável fica em `cmd/<nome>/`. Teremos `cmd/api` e, na Fase 5, `cmd/simulator`.
- Os argumentos de linha de comando ficam em `os.Args`, ou no pacote `flag`.

### 5. Erro como valor e o padrão `run() error`

> Em Java uma exceção sobe até o `main` e a JVM imprime o stack trace.
> Em Go o **erro é um valor de retorno** comum (tipo `error`), e quem chama decide o que fazer.
> Porque Go não tem exceções: o fluxo de erro fica explícito no código, linha a linha.

```go
func main() {
	if err := run(); err != nil {
		fmt.Fprintf(os.Stderr, "payhub api: %v\n", err)
		os.Exit(1)
	}
}
```

- `if err := run(); err != nil` declara `err` só dentro do `if` (escopo curto, prática comum).
- `nil` é o "zero value" de `error` e significa sucesso.
- **Por que não colocar tudo no `main`?** Porque `os.Exit` encerra o processo **sem rodar os
  `defer`** pendentes (que vamos usar para fechar banco, Redis etc.). Com a lógica dentro de
  `run()`, todos os `defer` rodam quando `run()` retorna, e só depois o `main` chama `os.Exit`.

### 6. Imports não usados são erro de compilação

Em Java um import sobrando gera no máximo um warning. Em Go, **import ou variável local
não usada não compila**. O `goimports` (configurado no VS Code) adiciona e remove imports
automaticamente ao salvar.

## Taskfile em uma linha

O Go não precisa dele. Ele só guarda comandos longos com nomes curtos e é a mesma interface
para você e para o CI. `task --list` mostra as tasks disponíveis.
`{{exeExt}}` vira `.exe` no Windows e nada no Linux, então o mesmo arquivo serve nos dois sistemas.

## Armadilhas comuns

- Importar `"payhub/internal/config"` em vez do caminho completo do módulo: não compila.
- Esquecer o `go mod tidy` depois de adicionar um import externo: erro `missing go.sum entry`.
- Usar `os.Exit` ou `log.Fatal` fora do `main`: pula os `defer` e mata o processo sem limpeza.
- Criar um pacote `utils`: em Go o nome do pacote faz parte da chamada (`config.Load()`),
  então prefira nomes que descrevem a responsabilidade.
